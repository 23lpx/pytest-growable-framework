# 架构审查（2026-10-11）

对 `framework/` 做的一次结构审查。尺子有两把：

- **《架构整洁之道》**（Clean Architecture）—— 同心圆分层、依赖规则
- **《代码整洁之道》**（Clean Code）—— 坏味道（死代码、函数长度、命名）

> 两本书同一个作者，但讲的东西不同：前者讲**分层与依赖方向**，后者讲**函数与命名**。
> 「同心圆」出自前者。

**结论先放**：分层是对的，依赖规则基本守住（**零循环依赖**），破口集中在
「内层依赖具体库」这一处 —— 已在同一天修掉。

---

## 一、方法

不靠肉眼看代码，用 AST 扫出**真实**的 import 图：

- 遍历 `framework/**/*.py`，解析每条 `import` / `from ... import`
- 区分「框架内部依赖」和「第三方库依赖」
- 只看图上的箭头 —— **箭头方向就是架构**，跟类图画得漂不漂亮无关

判据（贯穿全文）：

> **内层模块的 import 里，有没有出现具体库或外层类？**

## 二、同心圆：我们的分层

Clean Architecture 的四层是为**业务系统**设计的（Entities / Use Cases / …）。
套到**测试框架**上要做映射，不能生搬：

```
        ┌────────────────────────────────────────────────────┐
        │  Frameworks & Drivers        具体工具，最外          │
        │    client/HttpClient ← requests                    │
        │    reader/YamlRead   ← yaml                        │
        │    infra/logger      ← logging（stdlib）           │
        │    infra/report      ← allure                      │
        │  ┌──────────────────────────────────────────────┐  │
        │  │  Interface Adapters        适配：翻译          │  │
        │  │    handler/    适配器/ExecuteCase             │  │
        │  │    config/Config                              │  │
        │  │  ┌────────────────────────────────────────┐  │  │
        │  │  │  Use Cases         编排：一次测试怎么跑   │  │  │
        │  │  │    runner/CaseRunner（解析→发送→校验→提取）│  │  │
        │  │  │    runner/ScenarioRunner（顺序 + 步骤）  │  │  │
        │  │  │  ┌──────────────────────────────────┐  │  │  │
        │  │  │  │  Entities      内核概念，零框架依赖 │  │  │  │
        │  │  │  │    model/      用例模型            │  │  │  │
        │  │  │  │    context/    变量池 + 占位符      │  │  │  │
        │  │  │  │    contracts   契约（Protocol）     │  │  │  │
        │  │  │  │    exception/  异常体系            │  │  │  │
        │  │  │  └──────────────────────────────────┘  │  │  │
        │  │  └────────────────────────────────────────┘  │  │
        │  └──────────────────────────────────────────────┘  │
        └────────────────────────────────────────────────────┘
                ▲
                │  唯一允许 new 具体实现的地方（Composition Root）
                │
          conftest.py + testcase/
```

**映射时的取舍**（面试会问「测试框架的 Entity 是什么」）：

- 测试框架的「业务」是**执行一条用例**，不是 HTTP。所以 `HttpClient` **不是** Entity，
  它是「传输方式的细节」→ 最外层。
- 真正跨场景不变的内核是：**用例长什么样**（`model/`）、**值怎么在用例间流动**
  （`context/`）、**层与层的契约**（`contracts`）、**出错怎么表达**（`exception/`）。

## 三、依赖规则核对

| 规则 | 结果 |
|---|---|
| 依赖只能**由外向内** | ✅ 基本做到（3 处例外，见第五节） |
| 内层不依赖**具体库** | ✅ Entities / Use Cases / Adapters 现在 **零第三方依赖**（1 处例外） |
| 跨层走**契约**（Protocol） | ✅ `Sender` / `ResponseLike` / `CaseLike` / `VariableSource` |
| **无循环依赖** | ✅ 26 个文件，干净 DAG |
| 只有 **Composition Root** 能 `new` 具体实现 | ✅ 只有 `conftest.py` 和 `testcase/` |

### 各层实测的第三方依赖

| 层 | 模块 | 第三方 |
|---|---|---|
| Entities | `contracts` `exception/` `context/` `model/` `constants/` | **全是 `-`** |
| Use Cases | `runner/case_runner` | **`-`** |
| | `runner/scenario_runner` | `-`（仅 `infra/report`，见第五节） |
| Adapters | `handler/request` `handler/validation` `adapter/` `config` | **全是 `-`** |
| | `handler/extract` | `jsonpath`（见第五节） |
| Frameworks | `client` → `requests`；`reader` → `yaml`；`infra/report` → `allure` | 本职 / 已封装 |
| Composition | `conftest.py` `testcase/` | `pytest` `allure` |

> 这张表是审查前**没有**的：那时 `handler/` 三个文件都 `import requests`，
> `adapter/` 还 `import pytest`，`runner/` 还 `import client.HttpClient`。

## 四、本次修掉的

### A1 删死代码：`to_pytest_param()`

```python
from _pytest.mark.structures import ParameterSet   # 私有模块
...
def to_pytest_param(self) -> ParameterSet: ...      # 全仓无人调用
```

grep 全仓只有**定义**没有调用。删掉后 `adapter/` 对 pytest 零依赖 ——
收益不止「少一段死代码」，更甩掉了对 `_pytest` **私有结构**的脆弱依赖。

### A2 响应契约：`ResponseLike`

三个 handler 原本都 `from requests import Response`。内层依赖最外层的具体库，
换个 HTTP 库就要改三个文件。

`contracts.py` 加 `ResponseLike`（只要 `status_code` / `text` / `json()` 三个成员），
handler 改依赖它。顺带让单测里的 `FakeResponse` 从「鸭子类型骗类型检查」
变成**契约的合法实现**。

### B1 发送端口：`Sender`（依赖倒置）

```python
class Sender(Protocol):
    def request(self, method: str, path: str, **kwargs: Any) -> ResponseLike: ...
```

- `handler` / `runner` 依赖 `Sender`，**不 import `client.HttpClient`**
- `HttpClient._request` 公开成 `request`（端口需要它：case 的 method 是数据里的变量，
  走不了 `get` / `post` 这类固定方法）
- 配套：`HttpClient` 成为 `Sender` 契约的一个**具体实现**，由 `conftest` 注入

**效果**：`runner/` 和 `handler/` 对 `client/` 的依赖**归零** ——
全仓只有 `conftest` 知道 `HttpClient` 存在。

**验证方式**：新增 `tests/runner/test_case_runner.py`，注入一个**假 Sender**，
`CaseRunner` 的四步照跑不误（解析 / 发送 / 校验 / 提取、fail-fast、
参数位置推断全部覆盖）—— 全程不碰网络。**测试能跑通，本身就是倒置生效的证据。**

## 五、有意的逆流（别动）

审查后仍有三条箭头是「向内指」的，全部**刻意保留**：

| # | 位置 | 为什么留着 |
|---|---|---|
| ① | `model/` → `reader/` | 对**测试框架**而言，「用例存成 yaml」是**领域约定**，不是实现细节（类比：业务系统里「订单有金额」是领域，「订单存 MySQL」才是细节）。而且 `CaseModel.from_dict()` 已提供「不碰文件」的入口，真需要时能用 |
| ② | `runner/scenario_runner` → `infra/report` | Use Case 认识 allure。已用**薄封装**（`infra/report.py`）把耦合收在一个文件里，换 pytest-html 只改那里 |
| ③ | `handler/extract` → `jsonpath` | jsonpath **是算法实现**，它*就是*这个 handler 的活。抽象它没有意义 |

**判断「该不该倒置」的判据**：

> **能被一个简单契约替代的，才值得倒置。**
>
> `requests.Response` 是数据结构（三个成员就能描述）→ 该抽象；
> `jsonpath` 是算法（抽象出去只剩 `extract(data, expr)` 换汤不换药）→ 不该。

## 六、怎么复现这次审查

依赖图是**算**出来的，不是画的。把下面这段存成脚本（或直接 `python -c`）即可：

```python
import ast, pathlib, collections

root = pathlib.Path('framework')
files = sorted(p for p in root.rglob('*.py') if '__pycache__' not in p.as_posix())

internal, third_party = collections.defaultdict(set), collections.defaultdict(set)
for p in files:
    mod = p.as_posix()[:-3].replace('/', '.')
    tree = ast.parse(p.read_text(encoding='utf-8'))
    for node in ast.walk(tree):
        if isinstance(node, ast.ImportFrom) and node.module:
            (internal if node.module.startswith('framework') else third_party)[mod].add(node.module)
        elif isinstance(node, ast.Import):
            for a in node.names:
                (internal if a.name.startswith('framework') else third_party)[mod].add(a.name.split('.')[0])

for m in sorted(third_party):
    print(f'{m:44s} -> {", ".join(sorted(third_party[m]))}')
```

**审查之外还能顺手抓的**：

- **死代码**：`grep -rn "def 某方法" framework/` 之后，再 grep 调用点 —— 只有定义没有调用就是死的
- **私有 API 依赖**：`grep -rn "_pytest\|_internal\|\._" framework/ --include="*.py"`

## 附：这份文档的用法

不是一次性报告，是**基线**。后面加东西时拿它对照：

- 新加一个 handler / sender → 检查它有没有 import 具体库
- 想把某个第三方库抽成契约 → 先套第五节的判据
- 面试讲架构 → 第二节（映射取舍）+ 第三节（实测数据）+ 第五节（知道什么该改、什么不该改）
