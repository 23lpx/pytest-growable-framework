# 接口自动化测试框架核心设计

## 核心思想

测试数据与执行逻辑解耦。

-   数据层负责描述测试内容
-   框架负责解析、执行、校验
-   新增接口测试主要通过新增数据完成

目标：

> 一个执行框架，多份测试数据。

------------------------------------------------------------------------

## 整体模型

``` mermaid
flowchart TD
    A[yaml测试数据] --> B[Data Reader]
    B --> C[Case Model]

    C --> D[Test Runner]

    D --> E[Request Builder]
    D --> F[Http Client]
    D --> G[Extract Handler]
    D --> H[Validation Handler]

    F --> I[被测接口]
```

------------------------------------------------------------------------

## 模块职责

### Data Reader

职责：

将外部测试数据转换为统一模型。

输入：

    yaml/json/excel

输出：

    Case Model

数据来源变化不影响执行逻辑。

------------------------------------------------------------------------

### Case Model

职责：

作为数据与执行之间的稳定边界。

Runner只依赖模型，不关心数据来源。

------------------------------------------------------------------------

### Test Runner

职责：

执行固定测试流程：

    读取Case Model
            ↓
    构造请求
            ↓
    发送请求
            ↓
    提取数据
            ↓
    执行校验

------------------------------------------------------------------------

### Http Client

职责：

统一处理HTTP通信：

-   请求发送
-   session
-   timeout
-   日志
-   异常处理

------------------------------------------------------------------------

### Extract Handler

职责：

处理接口响应中的动态数据。

例如：

    response
       ↓
    extract token
       ↓
    Context保存

------------------------------------------------------------------------

### Validation Handler

职责：

根据测试规则执行结果校验。

例如：

``` yaml
validation:
  - contains:
      msg: 登录成功
```

------------------------------------------------------------------------

## 设计原则

### 1. 单向依赖

    Data
     ↓
    Model
     ↓
    Runner
     ↓
    Client

执行层不依赖具体数据格式。

------------------------------------------------------------------------

### 2. 固定流程，变化数据

接口测试逻辑保持统一：

    读取
     ↓
    执行
     ↓
    提取
     ↓
    校验

变化部分通过测试数据描述。

------------------------------------------------------------------------

### 3. 按需求扩展

基础能力稳定后，再根据实际需求增加：

-   Service
-   Scenario
-   Manager
-   Mock
-   Database等
